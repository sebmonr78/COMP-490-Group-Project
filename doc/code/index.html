Brain Dependency Check (simulation/setup/check_brain.sh)
        
Brain Dependency Check

Script      : setup/check_brain.sh   (Design: Brain setup)
Date        : Created 2026-10-28
Programmer  : Sebastian

DESCRIPTION
  Checks that everything DELTA's brain needs is installed, and installs
  whatever is missing or the wrong version. Safe to run as often as
  needed: what is already right is left alone. setup_brain.sh builds the
  env from nothing and stops if it already exists; this script is for an
  env that exists but may be incomplete or out of date.

  Usage (from simulation/):
      bash setup/check_brain.sh            check, then install what's missing
      bash setup/check_brain.sh --check    only check and report

  Checks, in order:
      1. conda                  cannot be installed from here: says how
      2. the `brain` conda env  Python 3.10, created if missing
      3. its Python packages    the pinned versions from setup_brain.sh
      4. that each one imports  a package can be installed and still broken
      5. the GPU                torch must see CUDA (driver 570+); reported only
      6. the model files        DA3, YOLOE, the Piper voice
      7. RTAB-Map               the `rtabmap` env and the compiled bridge,
                                built by setup/setup_rtabmap.sh if missing

  Exit code: 0 if everything is in place, 1 if anything is still missing.

IMPORTANT FUNCTIONS
  check_package NAME VERSION PIP_SPEC [needs-torch]
      In : pip package name, wanted version ("" = any), what to install,
           and whether it is built on torch.
      Out: prints ok / missing / wrong; installs PIP_SPEC if needed (not in
           --check mode); adds failures to PROBLEMS.
  installed_version NAME     Out: the installed version, or nothing.
  version_ok WANTED HAVE     True if HAVE matches WANTED, ignoring "+cu128".
  env_exists NAME            True if the conda env exists.
  brain_python / brain_pip   run Python / pip inside the `brain` env.
  bridge_works               True if the RTAB-Map bridge starts.

IMPORTANT DATA STRUCTURES
  Pinned versions (TORCH, XFORMERS, DA3_COMMIT, ULTRALYTICS, PIPER, ...):
      must match setup_brain.sh; change both together.
  PROBLEMS  (array): everything still not right, printed in the summary.
  INSTALLED (array): everything this run installed or fixed.
  TORCH_OK  (0/1):   whether the pinned torch is in place.

ALGORITHMS
  Check, then fix only what is wrong (idempotent): every item is compared
  with its pinned version first, so a second run changes nothing. Chosen
  over reinstalling everything, which would re-download several GB.

  Dependency order: torch is checked and installed first, and packages
  built against it (xformers, ultralytics, DA3) wait until it is right.
  Otherwise pip would pull a different torch from the ordinary index to
  satisfy them (not the CUDA 12.8 build). Once torch is in, it is repeated
  in every install so pip cannot "upgrade" it.

  Verify by import, not only by version: each module is imported in the
  env, since a package can be installed and still fail to load.

  No `set -e` on purpose: one failure must not stop the rest from being
  checked; the summary lists everything still wrong.

 
Login Page (app/static/login.html)
        
Login Page

  Page        : login.html   (Design: Log in State Diagram)
  Date        : Created 2026-10-19
  Programmer  : Sebastian

  DESCRIPTION
    The first page of the website. Log in, recover a forgotten email or
    password, and register a new account. Talks to the endpoints in
    main.py; a successful login goes to the dashboard (/dashboard).

  IMPORTANT FUNCTIONS (in the script at the bottom of the page)
    show(screenId)                  switches to one screen of the diagram
    send(url, body, form)           POSTs JSON; returns {ok, status, data},
                                    or null after showing the Server Error Box
    serverError(status, detail)     shows the Server Error Box
    markField(form, name, text)     marks one bad input, with its message
    One submit handler per form: log in, forgot email, forgot password,
    registration.

  IMPORTANT DATA STRUCTURES
    SCREENS      the ids of the 8 <section>s, one per state of the diagram
    FIELD_NAMES  input name -> label, for "Please fill out: ..." messages

  ALGORITHMS
    State machine: every state of the Log in State Diagram is one <section>;
    show() hides all but one, and any element with data-go="<screen>" moves
    to that screen. Chosen over separate pages because it mirrors the
    diagram one-to-one and switches instantly without reloading.

    Validation twice: empty fields are caught in the page before sending
    (quick feedback), and the backend checks everything again, since a page
    can be bypassed. The backend names every bad field, and each is marked.

 
Simulations (dashboard section) (app/static/index.html)
        
Simulations (dashboard section)

Component   : Simulation panel   (Design: Simulation Manager, page side)
Date        : Created 2026-10-21, last updated 2026-11-02
Programmer  : Sebastian

DESCRIPTION
  Lists the simulations, starts and stops them, and shows the running
  one: its live output, its window in the page (for "Run in browser"),
  and the physics twin's results once its flight ends. The work itself
  happens on the server (app/simulations.py).

IMPORTANT FUNCTIONS
  loadSimulations()          builds the table of simulations and buttons
  startSimulation(id, where) asks the server to start one, then polls
  stopSimulation()           asks the server to stop this session's run
  pollRun()                  fetches new output once a second while running
  showRun(run)               updates status, buttons, viewer, output
  showViewer(run)            puts the run's window (noVNC) in the page
  showResults(run)           shows the physics twin's numbers and plot

IMPORTANT DATA STRUCTURES
  run (from GET /api/simulations/run): number, title, status, lines,
    line_count, viewer {port, password}, results, server_running/max
  linesShown / shownRun / viewerShownFor / resultsShownFor: what is
    already on screen, so each update only adds what is new

ALGORITHMS
  Incremental polling: every second while a run is active, the page
  asks for output lines "since" the count it has, and appends only
  those. A new run number means a new run, so the output is cleared.
  Chosen over WebSockets because plain HTTP requests are simpler and
  work wherever the page itself loads; polling stops when the run ends.

  The window is an <iframe> of noVNC on the run's own viewer port, with
  that run's password, so each session sees only its own window.
